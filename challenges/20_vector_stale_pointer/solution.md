# 20_vector_stale_pointer

동적 배열(vector)의 원소를 가리키는 포인터를 받아 둔 뒤, 원소를 추가하는 과정에서 `realloc`으로 배열이 옮겨지면서 그 포인터가 **stale pointer**가 되는 문제를 분석하고 수정한 예제이다.

<br/>

## 개념 정리

- **vector** : 크기가 자동으로 늘어나는 동적 배열. C에서는 `data`, `len`, `cap`을 가진 구조체로 직접 구현하고, 원소를 추가하다 `len == cap`이 되면 `realloc`으로 공간을 키운다.
- **stale pointer** : 한때는 올바른 곳을 가리켰지만, 그 사이 상황이 바뀌어 더 이상 유효하지 않은 포인터. dangling pointer와 거의 같은 의미로 쓰인다.

vector 안의 원소를 가리키는 포인터를 받아 두었는데, 그 뒤에 원소를 추가하다가 `realloc`으로 배열이 다른 곳으로 옮겨지면 그 포인터는 옛 위치를 가리키는 stale pointer가 된다.

```
push 전:   data ──► [ A | B | C | D ]
                        ↑
                      ptr (B를 가리킴)

push 후:   data ──► [ A | B | C | D | E | _ | _ | _ ]   ← 새 위치
                    [   해제된 옛 영역   ]
                        ↑
                      ptr (여전히 옛 위치)
```

## 원인 분석

### 문제의 흐름

```c
for (int k = 0; k < 200000; k++) hist_add(&h, k);

Bucket *hot = &h.data[100000];   /* 1. 100000번 버킷의 주소를 받아 둔다 */
hot->count = 1;

for (int k = 200000; k < 600000; k++) hist_add(&h, k);   /* 2. 배열이 커지면서 이동 */

hot->count += 1000;              /* 3. 옛 주소에 쓰기 → SIGSEGV */
```

1. 원소 20만 개를 넣은 시점의 `cap`은 2¹⁸ = 262,144이다. 이때 `hot`에 100000번 버킷의 주소를 저장한다.
2. 이후 40만 개를 더 넣으면서 `cap`이 524,288 → 1,048,576으로 늘어나고, 그때마다 `hist_grow`의 `realloc`이 배열을 **다른 주소로 옮긴다.**
3. `h.data`는 새 주소로 갱신되지만, `hot`은 여전히 **옛 주소**를 가리킨다. 옛 영역은 이미 해제되어 매핑이 사라졌기 때문에, 그곳에 쓰는 순간 SIGSEGV가 발생한다.

<br/>

### `hist_grow`와 `realloc`

```c
static void hist_grow(Histogram *h) {
    h->cap = h->cap ? h->cap * 2 : 16;
    Bucket *p = realloc(h->data, h->cap * sizeof(Bucket));   /* 큰 배열은 이동(mmap 재배치) */
    if (!p) { perror("realloc"); free(h->data); exit(1); }
    h->data = p;   /* realloc은 블록을 다른 주소로 옮길 수 있으므로 새 주소로 갱신 */
}
```

`realloc`으로 크기를 바꿀 때 블록이 다른 주소로 옮겨지는 일이 흔하다. 즉 `p`는 기존 `h->data`와 다른 주소일 가능성이 높다. `h->data = p;`는 구조체 안의 포인터만 갱신할 뿐, `hot`처럼 **밖에서 따로 들고 있던 포인터까지 고쳐 주지는 않는다.** 이것이 이번 문제의 핵심이다.

### 왜 "큰 배열은 이동"한다고 할까: malloc이 메모리를 구하는 두 가지 방법

1. **힙에서 잘라 주기**
   운영체제에게서 큰 덩어리(힙)를 미리 받아 놓고, 요청이 올 때마다 거기서 조금씩 잘라 준다. 여러 블록이 한 덩어리 안에 옆집처럼 붙어 산다.
   ```
   힙: [블록A][블록B][블록C][  빈 공간  ]
   ```

2. **운영체제에게서 따로 받아 오기 (mmap)**
   요청이 너무 크면 힙에서 자르지 않고, 운영체제에게서 **그 블록만을 위한 전용 공간**을 직접 받아 온다.
   ```
   힙:    [블록A][블록B][블록C]
            ...떨어진 곳...
   mmap:  [      큰 블록 D (혼자)      ]
   ```

두 방법을 가르는 기준은 glibc의 **mmap 임계값(`M_MMAP_THRESHOLD`)** 이고, 기본값은 **128KB**이다. 요청 크기가 이보다 작으면 일반 힙에서, 크거나 같으면 `mmap`으로 따로 할당한다. 다만 이 값은 고정이 아니며, `mmap`으로 받은 큰 블록이 해제되면 임계값을 그 크기만큼 올리는 식으로 실행 중에 동적으로 조정된다.

이 코드의 `Bucket`은 16바이트(`int` 4 + 패딩 4 + `long` 8)이므로, 대략 8,192개를 넘는 시점부터 배열은 힙이 아닌 `mmap` 영역에 할당된다. 그 뒤로는 커질 때마다 새 위치로 옮겨지는 일이 잦기 때문에 "큰 배열은 이동한다"는 주석이 붙은 것이다.

**결론적으로, 작은 배열도 옮겨질 수 있으므로 크기와 상관없이 `realloc` 후에는 주소가 바뀔 수 있다고 가정해야 한다.**


<br/>


## 해결

### 방법 1. 포인터 재취득

```c
Bucket *hot = &h.data[100000];
...
hot = &h.data[100000];   /* 배열이 커진 뒤 현재 주소를 다시 받아 온다 */
hot->count += 1000;
```

새 변수를 선언하는 것이 아니라, 이미 있는 `hot`에 **현재 배열 기준의 주소를 다시 대입**하는 방식이다.

### 방법 2. 인덱스 보관 (최종 선택)

```c
size_t hot_index = 100000;
h.data[hot_index].count = 1;

for (int k = 200000; k < 600000; k++) hist_add(&h, k);

h.data[hot_index].count += 1000;

printf("hot=%ld total=%ld len=%zu\n", h.data[hot_index].count, hist_total(&h), h.len);
```

포인터 대신 **몇 번째 칸인지(인덱스)** 를 들고 있다가, 접근할 때마다 `h.data[hot_index]`로 주소를 새로 계산한다.

<br/>

## 인덱스 방식이 더 나은 이유

가장 큰 장점은 **배열이 어디로 옮겨지든 계속 유효하다**는 점이다.

포인터는 **절대 주소**(메모리 0xaaaa…번지)를 기억하고, 인덱스는 **상대 위치**(배열의 100000번째 칸)를 기억한다. `realloc`으로 배열이 옮겨지면 절대 주소는 틀려지지만, "몇 번째 칸"이라는 사실은 그대로다. 인덱스로 접근할 때마다 `h.data[i]`가 **현재 시작 주소 + i**를 새로 계산하므로 항상 올바른 곳에 닿는다.

**인덱스의 장점**

- **범위 검사가 쉬움** : `if (i < h.len)` 한 줄로 유효한 원소인지 확인할 수 있다. 포인터는 그 주소가 배열 안인지 판단하기 번거롭다.
- **저장·전송이 쉬움** : 인덱스는 그냥 숫자라서 파일에 저장하거나 다른 프로세스로 보내도 의미가 유지된다.
- **크기를 줄일 수 있음** : 원소 수가 충분히 작으면 `uint32_t` 인덱스(4바이트)를 써서 64비트 포인터(8바이트)보다 메모리를 아낄 수 있다.
- **디버깅이 쉬움** : `hot_index = 100000`은 바로 읽히지만, 메모리 주소는 무엇을 가리키는지 바로 알기 어렵다.

**인덱스의 한계**

- **원소를 삭제하거나 순서를 바꾸면 틀어짐** : 중간 원소를 지우고 뒤를 당기면, 인덱스 100000은 다른 원소를 가리키게 된다. 크래시 없이 조용히 틀린 값을 쓰게 되므로 오히려 찾기 어려운 버그가 될 수 있다. 이런 경우 인덱스에 세대 번호를 붙여 검증하는 **generational index** 방식으로 해결할 수 있다.

**정리**

- 이번 문제처럼 **배열이 커지면서 옮겨질 수 있는 상황**에서는 인덱스가 확실히 안전하다. 원소가 삭제·재배치되는 상황이라면 인덱스도 따로 주의가 필요하다.
- 포인터 재취득은 인덱스 방식의 **차선책**에 가깝다. 재취득하려면 결국 위치(인덱스)를 알고 있어야 하므로, 처음부터 인덱스를 들고 있는 편이 더 단순하다. 또한 배열이 커질 수 있는 모든 지점 뒤에서 잊지 않고 다시 받아 와야 해서 실수하기 쉽다.
- 동적 배열의 원소를 구조체 필드 등에 **오래 저장해 두는** 경우에는 사실상 인덱스가 표준이다. 반대로 받자마자 쓰고 끝나는 짧은 구간이라면 포인터를 써도 괜찮다.

## 남은 개선점

`hist_add`는 여전히 새 버킷의 **포인터**를 반환한다. 지금 `main`에서는 반환값을 쓰지 않아 문제가 없지만, 나중에 누군가 이 포인터를 받아 들고 있으면 같은 버그가 재발할 수 있다. 인덱스를 반환하도록 바꾸면 호출하는 쪽이 실수할 여지를 없앨 수 있다.
